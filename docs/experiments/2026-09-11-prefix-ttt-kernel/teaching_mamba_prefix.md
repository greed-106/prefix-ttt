# 从前缀递推到高效 GPU 实现：Mamba 对 Prefix-TTT 的启发

本章组面向能够阅读矩阵乘法、但不熟悉 GPU scan 的研究者。它回答一个具体问题：已经是线性复杂度的 Prefix-TTT，为什么仍可能比二次复杂度的 FlashAttention 慢，怎样在不改变已训练函数的前提下改进实现？论文背景与原始实验边界见 [Mamba 阅读](mamba_reading.md)。本文的数值容量是公式推算，不是运行测量；“候选”是本阶段要验证的方案，不代表已进入生产。

## 第一章：先决定我们到底要算什么

考虑一个注意力头，省略 batch 与 head 下标。输入经过 QKV 投影和 RoPE 后，得到 $q_t,k_t,v_t$。Prefix-TTT 将前两者映射为 $r$ 维特征，记为 $\tilde q_t=\phi(q_t)$、$\tilde k_t=\phi(k_t)$，再维护矩阵状态：

$$
S_t=S_{t-1}+\eta\tilde k_tv_t^\top,\qquad
m_t=\tilde q_t^\top S_t,\qquad \eta=1/128.
$$

状态的行表示 key 特征坐标，列表示 value 坐标。一次外积写入把 key 与 value 关联起来，query 再沿 key 特征维度读出。因为先写再读，展开式是

$$
m_t=\tilde q_t^\top S_0+
\eta\sum_{i=1}^{t}(\tilde q_t^\top\tilde k_i)v_i.
$$

这个式子既像注意力，也暴露了区别：权重来自特征内积，没有 softmax 行归一化。本项目后续对 memory 向量做 RMS，并用 signed gate 调制，再加 Local-32；这也不等同于在线性注意力核心中加一个分母。优化只能换求值方式，不能混淆这些函数。

用只有三个 token 的例子检查因果关系最直接：第一项读取 $S_0+\Delta S_1$，第二项读取 $S_0+\Delta S_1+\Delta S_2$，第三项才读取三个更新。任何先读后写实现都会漏掉当前项；任何把最后状态直接用于所有位置的实现都会泄露未来。这两类错误可以在很小的 FP64 oracle 中发现，无需启动大模型。

完整替换层还包括

$$
\phi(x)=\mathrm{RMS}\bigl(\mathrm{SiLU}(xA_\phi)\odot(xB_\phi)\bigr),
$$

$$
z_t=\mathrm{Local32}(q,k,v)_t+
g(x_t)\odot\mathrm{RMS}(m_t),\qquad y_t=W_Oz_t.
$$

这里 $g$ 为每个 head 一个标量的有符号线性门控，通过广播作用于该 head 的所有 value 坐标。它不是 sigmoid 遗忘门；改变它会改变模型。Local-32 的第 33 个有效 token 开始新块，不再读取前 32 个有效 token 的局部 K/V，但它们的全局信息仍在 $S_t$ 中。理解这两个记忆系统分工，才能正确测量缓存成本。

## 第二章：为什么递推也可以并行

表面看，计算 $S_3$ 必须等待 $S_2$，后者又必须等待 $S_1$。真正的依赖却只是加法：所有 $\Delta S_t=\eta\tilde k_tv_t^\top$ 都能从已知输入独立产生。于是每个状态是对应前缀的和。

对于四个更新，可以先并行组合 $(\Delta S_1+\Delta S_2)$ 与 $(\Delta S_3+\Delta S_4)$，再合并更大前缀。树形算法依赖加法结合律；实数运算中与逐步加法相同，浮点数中会因求和顺序不同出现舍入差异。这个区分贯穿后面的正确性判断：代数证明是必要条件，数值验证仍不可省略。

Mamba 使用更一般的仿射递推

$$
h_t=a_t\odot h_{t-1}+b_t.
$$

若把一个前缀压缩成一对 $(a,b)$，前后两段也可以组合为

$$
(a_1,b_1)\star(a_2,b_2)
=\bigl(a_2\odot a_1,\;a_2\odot b_1+b_2\bigr).
$$

这个运算保持顺序且满足结合律，因此可以扫描。本项目是“旧状态系数恒为 1”的特殊情形，不过状态本身是矩阵。共同点是前缀摘要可组合；区别是摘要的大小与适合的计算单元。对每个矩阵元素机械地运行 scan 虽然正确，却未必是 GPU 上最快的形式。

## 第三章：把扫描搬上 GPU，首先遇到的是内存

GPU 的 HBM 容量大，适合保存模型参数和长序列；每个计算单元附近的寄存器、共享内存容量小，却能以更低代价反复访问。一个内核若只做少量乘加，却不断读写很大的中间量，算术单元可能一直等数据。Mamba 的核心启发就是让扩展状态在片上产生、消费，只把必要结果写回 HBM。

以本项目的 32 个 head、每头 $128\times128$、FP32 状态为例：

$$
32\times128\times128\times4\ \mathrm{bytes}=2\ \mathrm{MiB}.
$$

单样本的最终状态只有 2 MiB；如果给长度 32768 的每个位置都写一个完整状态，体积却是

$$
32768\times2\ \mathrm{MiB}=64\ \mathrm{GiB}.
$$

这还不含特征和输出。线性随长度增长也可以有很大的常数。我们想去掉的是这种逐 token 的矩阵状态物化，而不是仅把 Python 循环换成更多并行张量操作。

也不能直接宣布“整个状态都常驻共享内存”。单个 head 的 FP32 状态已是 64 KiB，还需要 Q/K/V tile、输出累加器与临时矩阵。寄存器过多会降低可同时驻留的线程块数量，甚至溢出到较慢存储；共享内存过多同样限制并发。现实实现常需沿 key/value 维切分状态，或在若干块边界写回摘要。好的融合必须有资源预算，内核数最少不必然最快。

Mamba 的原始 scan 多为逐元素操作，而本项目的矩阵状态天然含 GEMM。Tensor Core 可高效处理 BF16 输入及 FP32 累加的块矩阵乘法，因此下一步是把数学式整理成适合 GEMM 的样子。FP32 状态存储仍保留；不能为了快直接将持久状态降为 BF16。

## 第四章：把一长串 token 改写为块间与块内两部分

设每块有 $c$ 个 token。第 $j$ 块的特征与 value 堆成 $Q_j,K_j\in\mathbb{R}^{c\times r}$、$V_j\in\mathbb{R}^{c\times d_v}$。用 $S_j^{\mathrm{in}}$ 表示进入该块前的状态，定义块更新

$$
U_j=\eta K_j^\top V_j.
$$

块的出口状态为

$$
S_j^{\mathrm{out}}=S_j^{\mathrm{in}}+U_j,
\qquad
S_j^{\mathrm{in}}=S_0+\sum_{i<j}U_i.
$$

注意入口使用不包含当前块的前缀。再令 $L_c$ 是包含对角线的下三角 0/1 矩阵，整块输出可写成

$$
M_j=Q_jS_j^{\mathrm{in}}+
\eta\bigl((Q_jK_j^\top)\odot L_c\bigr)V_j.
$$

第一项读取所有更早块的摘要，第二项只看当前块中不晚于自己的 token。把第 $p$ 行展开，就恰好恢复第一章的递推公式。这个式子也说明两种 scan 的 off-by-one 错误：若第一项错用出口状态，当前块会被重复计入且包含未来；若第二项去掉对角线，就变成先读后写。

由此得到三个自然步骤：块更新用 $K_j^\top V_j$ 的 GEMM；块间摘要做前缀组合；历史读出和块内读出再用 GEMM。实现可以重叠或融合部分步骤，但无需构造 $[T,r,d_v]$ 的逐 token 状态。

假设所有块入口状态都写回 HBM，其规模约为

$$
O\left(BH\left\lceil\frac{T}{c}\right\rceil rd_v\right).
$$

这比逐 token 状态少约 $c$ 倍，却仍可能显著。例如上面的长度 32768、块 64，完整边界状态数组约为 1 GiB/样本；实际内核是否保存这些状态、保存何种 dtype、是否按 tile 组织，必须读源码与 profiler 确认。这是上限式的数据流估算，不是当前 FLA 的实测 allocated 数字。

本项目既有 FLA 已利用分块结构。因此本轮不能把上面代数重写本身当成新增成果。真正要比较的是已有实现与候选在块尺寸、状态 IO、张量布局和外层调用上的差异。

## 第五章：块大小为什么需要测，而不能从公式中拍板

按每头估算，块摘要与历史读出分别具有 $O(Trd_v)$ 级别的计算；块内两次乘法的成本合计为 $O(Tc(r+d_v))$。增大 $c$ 减少块边界数量和调度开销，却增加块内两两交互，并提高片上工作集。

因此块 128 不一定比 64 快，64 也不一定比 32 快。短序列可能没有足够的块提供并行度，大 batch 则改变可调度任务数；尾块不满还会影响填充比例。形状 640 与 1536 不能完全代表 32768，batch 1 也不能代表 batch 4。需要保留每个配置的原始延迟，才能判断某个块选择是普遍收益还是局部现象。

Mamba 所强调的融合也有类似取舍。把值缩放、无效位置置零、特征尾部或 readout 的连续逐元素操作合并，通常能减少读写；把大型 GEMM 生硬塞进单个自定义内核，则可能失去成熟库的高效率。应先分解时间，找出真正热点，再逐项实现和消融。

起始版本已经为单 token decode 合并四路特征投影。把思想扩展到 prefill 时，要同时核算为 Q/K 打包或转置的成本，不能只计一次合批 GEMM 的时间。准备期权重副本应排除在请求计时外，同时单独报告常驻显存；权重修改后必须重新准备，避免用旧副本制造“速度提升”。

对全有效输入，可以建立不做无效 mask 的路径，但应由调用上下文提供可信信息，或使用既有接口能确定的条件。每次在热路径调用 `.all().item()` 再选择分支可能引入 CPU/GPU 同步，抵消节省的内核。对于 padding、空洞和空行，通用路径仍要保留原语义；没有执行的通用策略不等于被删除。

## 第六章：为什么线性复杂度仍可能输给 FlashAttention

设模型隐藏维度 $D=Hd$。标准 Q/K/V/O 四个稠密投影约需要 $8BTD^2$ 次浮点运算，两种完整层都承担这一公共项。TTT 还增加 Q/K 的双特征投影、memory RMS、门控和 Local-32。若仅比较核心线性注意力与核心 Flash SDPA，就会遗漏这些新增成本。

用一个仅用于解释的延迟模型表示：

$$
t_{\mathrm{MHA}}(T)=t_{\mathrm{common}}(T)+aT^2+bT+c_0,
$$

$$
t_{\mathrm{TTT}}(T)=t_{\mathrm{common}}(T)+dT+e_0.
$$

其中 $d$ 包含特征、局部注意力和状态路径；$e_0$ 包含尚未摊薄的启动与包装成本。实际系数会随形状、GPU 饱和度和后端改变，公式不能直接用于预测交叉点。它只解释：即使长期渐近趋势有利，短序列的二次项还小时，额外线性项和固定成本仍能让 TTT 更慢。

FlashAttention 也不是把完整 $T\times T$ 注意力矩阵存入显存的朴素实现。它以分块和在线 softmax 降低 IO，所以“TTT 缓存固定”不代表 prefill 显存一定小几个数量级。应分别测持久 KV/状态缓存与运行临时显存。

例如当前形状的 BF16 MHA K/V 每 token 每样本为 $2\times4096\times2=16384$ bytes；TTT 全局状态固定为 2 MiB，另有 Local-32 的残留 K/V 和元数据。容量的相等点是存储算术，不是延迟交叉点；读带宽、复用方式和算子效率仍然不同。

## 第七章：把公平比较写成可以复核的实验

核心算子实验回答“前缀计算本身有没有收益”，完整层实验回答“替换注意力后有没有收益”。二者都要保留当前 FLA、优化候选与 Flash SDPA 三臂；两种不同模型函数之间不检查输出相等，只对同一 TTT 函数的不同实现做数值检查。

本阶段约定固定 BF16 输入、隐藏维度 4096、32 个头和头维度 128，关闭 dropout，双方共享 QKV/O 权重与输入。TTT 的 gate 需要非零，避免某个未训练初始化使 memory 分支对输出没有影响。完整模块计入 QKV、RoPE、所有注意力分支、门控、输出投影与可接续 decode 的缓存生成；共同 MLP 不包含在该模块定义中。

每次调用应从空请求缓存开始。只复用固定输入和权重，不复用前一次 prefill 已累积的状态。若连续重复输入写入同一个缓存，时间、输出和内存都会偏离“同一前缀请求”的定义。四层实验则让一层输出进入下一层，检查单层结论在实际串联中是否成立，不能只把单层数字乘四。

计时先排除加载、编译与预热，然后在同卡同进程交替运行比较臂，减少温度与频率漂移的偏差。CUDA Event 测设备时间，带同步的墙钟测调用开销；profiler 单独运行，避免插桩改变主结果。五轮各 20 次、预热 20 次的原始采样应完整保存，中位数和 P10/P90 由这些样本计算。稳定领先使用完整层至少 1.05 倍且五轮均领先的判据；若速度随长度不单调，报告区间，不创造一个不存在的单一交叉点。

强制 Flash SDPA 后端并记录实际 kernel，是保证基线身份的必要操作。若后端不支持某个配置，应记录失败，不能静默回退到较慢实现再声称超过 FlashAttention。主结果仅适用于锁定环境和执行的形状；论文中的 A100、维度 1024、状态 16 的 scan 比较不能替代这里的 H100 完整层比较。

## 第八章：数值、缓存和真实模型构成三层验收

第一层是代数与基本数值。用 FP64 小模型比较顺序 oracle 与候选，覆盖非零初态、块边界前后、非整块长度和不同 query/key/value 内容。要同时检查所有输出和最终状态；只检查最后状态会漏掉因果读出错误。

第二层是既有实现契约。FP32 状态、$\eta=1/128$ 只施加一次、输入状态不被原地污染、全量 prefill 与分段 prefill 后接 decode 的一致性都应检查。padding 和空洞不能产生写入，Local-32 按有效位置计数，空行保持旧状态；非连续输入要么正确处理，要么明确走现有兼容路径。autograd 继续使用被验证的训练实现，不能因推理优化意外截断梯度。

融合时还要区分“FP32 累加”与“完全 FP32 求值”。BF16 投影、SiLU、乘积、RMS 返回和门控之间原本存在舍入点；把整条链都留在 FP32 最后一次舍入，即使看起来更精确，也是在改变现有数值程序。不同 GEMM 的求和顺序、Tensor Core 输入精度、FMA 与禁用/启用 TF32 都可能改变结果。因此沿用既有容差，同时记录最大绝对误差、相对 L2 误差和非有限值，不因某候选更快而放宽标准。

第三层是真实 checkpoint。随机输入适合隔离性能，却无法保证在真实权重分布下没有误差放大。用加载后的层权重和固定隐藏状态复测，并在生产接入前对受影响的完整版本执行质量回归；回答差异和官方分数一起报告。上阶段曾出现快内核导致真实质量回归的记录，正说明小张量公式正确不能代替模型级证据。

本轮不新增反向内核，也不把输入相关遗忘或低秩近似作为实现优化混入。最终结论只由已经执行且有配置、日志、状态文件支撑的实验产生：可能是完整层在长序列稳定领先，也可能只有核心算子领先，或某候选没有净收益。每一种结果都能回答具体瓶颈在哪里，并为下一轮提供可信起点。
